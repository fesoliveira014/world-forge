# v2.2.1 — Reservoir generation stall

The v2.2 nested-lake solver restarted a closed receiving subtree whenever another pond supplied it with spill. A chain of such ponds could evaluate the same subtree twice at every depth, making work exponential. This is a demonstrated regression; the exact seed/settings of the reported browser run were unavailable.

The fix retains each basin’s settled children. New water updates its receiving branch, and only the increase in outflow crosses the next saddle. When children merge, their parent balances its own inflow, excluding duplicated internal transfers. An already merged lake rebalances directly. DFS leaf intervals select the affected branch, and final lake records are collected once. Terrain, climate, resolution limits, and river rules are unchanged.

## Focused verification

- A 65-corner chain of 33 ponds reached 41,771,008 recursive calls in the previous implementation before instrumentation stopped it after five seconds. The fixed solver completes the same case in about 3.4 ms and preserves the expected terminal inflow and reservoir ledger. This is a synthetic regression fixture, not a claim about the user’s exact world.
- At 655,362 surface cells and 40,962 simulation cells, the default seed’s cached river input takes 3.37 seconds with the old solver and 0.76 seconds with the fix. All receivers and lake levels match. Maximum discharge difference is 2.3 × 10⁻¹³ m³/s; both produce 2,271 lakes. Global and individual reservoir accounting remain balanced.
- TypeScript, the existing four core tests plus the new pond-chain regression, and the production build are the checks. No browser QA or broad seed sweep was performed.

The default maximum-detail full pipeline completed in approximately two minutes in the diagnostic environment before this fix; most time was in its two weather passes. That run did not reproduce the reported ten-minute stall. The pond-chain fixture establishes a specific slowdown that depends on basin structure. Weather detail affects terrain and water inputs, but the rivers stage does not run weather iterations itself. Browser hardware, seed, and generation parameters still affect total duration.

After the update, refresh the app before starting a new generation: an already-running worker continues using its loaded code. Detailed observations are in [revision-2.2.1-measurements.json](../../observations/history/revision-2.2.1-measurements.json).

# v2.10.0 — Minerals, gemstones, and land fertility

World Forge now publishes a mineral endowment and a fertility field after the existing environmental generation. The application and generator versions are 2.10.0; the resource recipe is `resources-1`.

## Using the extension

Regenerate an existing project, then open **Resources → Minerals & gemstones** or **Resources → Fertility**. The mineral panel filters by resource and provides a deposit selector alongside clicking markers. Inspect a deposit for its initial quantity, approximate extent radius, formation association, and current land/water location. The selected outline is its physical extent; the screen marker encodes quantity independently.

Under **Minerals & fertility**, **Deposit frequency** ranges from 0–4× and **Deposit amount** from 0.1–4×. Both default to 1. Frequency zero omits deposits but still computes fertility. Changing the amount multiplier preserves locations. Generate applies these settings; changing a layer, resource filter, camera, or season does not regenerate resources.

Fertility uses a fixed 0–100 scale. The cell inspector shows the cell mean, surrounding-land potential, local corridor peak and mean, corridor coverage, contributor values, and limitations. Blue denotes water and pale cells denote permanent ice. The fertility field is annual/general potential, independent of the selected display season.

## Retained state and ownership

`World.resources` owns `recipe`, `Deposit[] deposits`, and `Float32Array fertility`. Deposits contain an ID, resource type, unit-sphere anchor, approximate extent radius in kilometres, amount, and formation cause. One deposit owns one amount even if its footprint crosses multiple cells. There are no per-resource full-resolution inventory arrays.

The environmental arrays remain borrowed inputs. The existing worker transfers the fertility buffer through its recursive buffer collector; deposit objects use the completion message's normal structured clone. Reported buffer memory excludes JavaScript object overhead and GPU copies.

## Placement algorithm

The initial palette is copper, tin, iron, gold, and a combined ruby/sapphire family. The preset table supplies frequency, coherent-mask scale, clustering radius, bounded amount/extent ranges, and allowed causes. These are worldbuilding assumptions, not simulated mineral chemistry.

For each resource, scan process cells and combine geological suitability with a coherent seeded eligibility mask. Continental context, magmatic/volcanic signals, positive inherited deformation/current uplift, and incident boundary edges supply the broad setting. `Geology.boundary` is indexed by edges. Tin uses a rarer continental intrusive-compatible mask; inherited iron uses retained continental/reference context independently of present magmatic boundaries.

Inherited masks sample through `referencePoint()` for the selected retained crust. Opened ocean does not inherit an ancient continental preset. Without crust history, current coordinates provide the reference. The in-scope process-only `referenceOceanMask` supplies initial land eligibility; neither surface terrain nor final climate enters primary placement.

Each weight is `suitability × cell area in km²`. Total eligible area sets an expected regional cluster count, converted to an integer by seeded stochastic rounding. A cumulative table and binary search choose regional anchors. Each anchor produces 1–4 candidates within a physical spherical disk, with at most six local eligibility attempts per candidate.

Amount and extent use separate per-deposit random streams. Amount is `round((minimum + (maximum-minimum) × random²) × depositAmount)`. Each family has independent placement/eligibility/attribute namespaces, so adding gemstones does not perturb copper. Amounts are abstract units within a resource, not ore tonnage, quality, or comparative economic value.

With process inputs and recipe fixed, surface subdivision preserves all primary deposit records. Detailed erosion or lakes can change whether an anchor is under water; that surface association is reported without moving or deleting the endowment. Geological duration, process resolution, or placement-rule changes can produce a different baseline.

## Fertility algorithm

`evaluateFertilityCell()` is shared by generation and inspection. The bulk pass reuses one evaluation record and retains only the final Float32 scores.

The initial contributors are:

- Sediment: `1 − exp(−max(0, sediment)/12 m)`. Seasonal alluvial coverage can provide a capped benefit inside a river corridor. Recorded delta sediment is not added a second time.
- Rain: `clamp(rain / max(1 mm, PET) / 0.9)`.
- Freshwater: supported reaches use `1 − exp(−supportFlow/5 m³/s)`. Eligible inland shores use 0.8 access within a local physical footprint, capped at 2.5 km and restricted by bank rise. Ocean proximity receives no credit. Inland water is assumed fresh.
- Volcanic ground: a saturating construction signal multiplied by `1 − exp(−volcanicAge/2 Myr)`. Exposed substantial recent cover applies a separate limitation; sediment cover weakens that limitation. These are broad age/cover proxies, not soil-development dates.

The shared rule is:

```text
ground = clamp(0.35 + 0.40*sediment + 0.25*volcanic)
water = 1 - (1-rain)*(1-freshwater)
potential = 100 * ground * water * suitability
```

Growing-season temperature, slope, saturation, and fresh volcanic cover limit general suitability. The local corridor uses channel slope and its already terrain-limited footprint instead of applying the enclosing cell's slope twice.

Compute surrounding potential and corridor core potential separately. The existing bank fade contributes 65% of the positive local enhancement to the corridor mean. Then:

```text
corridorMean = regional + 0.65 * max(0, corridorCore - regional)
cellMean = (exposedLandFraction - corridorFraction) * regional
         + corridorFraction * corridorMean
```

The corridor uses a capped shared envelope of persistent river and eligible shore coverage; seasonal flood coverage overlaps the persistent banks. This is an approximate footprint, not a polygon union or land-parcel model. Cells classified as standing water or permanent ice receive zero. Remaining subcell lake coverage also contributes zero land potential.

The fertility palette bypasses decorative bank textures and delta recoloring, keeping colors tied to the score. The accepted natural, lake, river, and delta rendering is retained.

## Compatibility and checks

Project files remain generation recipes. Export adds `resourceRecipe`; import explicitly preserves 2.9.0 compatibility and supplies defaults for missing controls. A differing resource recipe produces an explicit regeneration notice. The identifier does not retain old algorithms or freeze historical extraction.

All 27 tests pass, including four new checks for primary stability, local fertility behavior and exclusions, marker picking across the globe horizon/map seam, and project compatibility. TypeScript checking and the production build pass. A before/after AETHER-0003 comparison at 10,242 surface cells produced identical hashes for the full environmental fields, excluding resource and runtime metadata.

The new stage took 16.1 ms in that smaller comparison and generated 337 deposits. Timings are observations from this environment, not performance guarantees. Browser visual testing was not performed.

## Limits

Formation causes describe retrospective procedural associations. No dated geological episode log, new simulation during tectonic steps, secondary mineral transport, purity, concentration, extraction, or economy is added. Fertility does not predict crop yield, create irrigation, consume water, or establish population capacity. The TypeScript data/function boundary remains suitable for a later C3 port.
